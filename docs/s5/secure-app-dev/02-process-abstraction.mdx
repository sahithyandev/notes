A program is not just source code. Under execution it becomes a process, a dynamic abstraction describing the state required to describe a running [program](/s3/operating-systems/process#program), distinct from the program it instantiates. A process's state splits into 3 contexts, each a distinct target when reasoning about exploits.

- Memory context  
  Code, data, dynamically allocated memory. Corrupted by memory safety violations.
- Hardware context  
  Registers, program counter, stack pointer. Corrupting these hijacks control flow.
- OS context  
  Process ID, process state, resources used. Governs what the process is authorized to access.

<Note>

Process states, transitions, and the full context breakdown are covered under [process states](/s3/operating-systems/process#process-states) and [process context](/s3/operating-systems/process#context).

</Note>

## Process Control Block

The Process Control Block (PCB) stores all 3 contexts for a single process. The kernel maintains 1 PCB per process, conceptually organized as a single process table.

Design issues:

- Scalability  
  How many concurrent processes the table can support.
- Efficiency  
  Access must be efficient with minimum space wastage.
