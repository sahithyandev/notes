Discretionary Access Control (DAC) is Linux's traditional security model. A process running with root privileges is granted unrestricted access, while other accounts can do much less. Attackers therefore target root privileges.

In Linux, most system resources, including memory, device drivers, and named pipes, are represented as files, so file system security is central to the model.

The kernel enforces Linux's DAC. Kernel space is never swapped to disk, and only root may load or unload kernel modules.

## Users and Groups

- User account  
  Represents an entity, human or process, capable of using files. Details are kept in `/etc/passwd`.
- Group account  
  A list of user accounts. A user has 1 main group and may belong to other groups. Details are kept in `/etc/group`.

Users and groups are managed with `useradd`, `usermod`, `userdel`, and the equivalent `group*` commands.

## File Permissions

Every file has 2 owners, a user and a group, plus a third permission set for all other users. Each of the 3 sets carries read, write, and execute permissions, in the order user, group, other.

Permissions are set with `chmod`. Numerically, each set is 1 octal digit: read contributes 4, write 2, execute 1, summed per set (user, group, other).

### Directory Permissions

Same permissions are applied to the directory.

- Read  
  List the directory's contents.
- Write  
  Create or delete files in the directory.
- Execute  
  Use anything in the directory, or change the working directory into it.

### Sticky Bit

Originally used to lock a file in memory, now applied to directories to restrict deletion. If set, a user must own a file to delete it, even with write permission on the directory. Set with `chmod +t`. Applies only to that directory, not to child directories.

The sticky bit has no character position of its own. It overloads the other-execute position in the listing: `t` if that execute bit is also set, `T` if not.

### SetUID and SetGID

- SetUID  
  The program runs with the privileges of its owner, regardless of who executes it.
- SetGID  
  The program runs as a member of the group that owns it, regardless of who executes it.

SetUID and SetGID are permission bits on the executable file, like the sticky bit, not functions the program calls. The kernel applies them during `exec()`: it sets the process's effective UID or GID from the file's owner or group before any of the program's own code runs.

Like the sticky bit, neither has a character position of its own. SetUID overloads the user-execute position, SetGID the group-execute position: `s` if the underlying execute bit is also set, `S` if not.

SetUID has no effect on directories. SetGID on a directory causes any file created inside to inherit the directory's group, useful when users share files across a common group without manually changing ownership.

<Note>

SetUID and SetGID are dangerous when set on a file owned by root or another privileged account, and should only be used on executable binaries, not shell scripts.

</Note>

## Setuid Root Programs

A setuid root program runs as root no matter who executes it, used to give unprivileged users controlled access to privileged resources. Such programs must be very carefully written.

A running process may separately call the `setuid()` or `setgid()` system calls to change its own UID or GID. A setuid root program typically calls `setuid()` itself once its privileged work is done, permanently dropping back to an unprivileged UID for the remainder of execution.

A software bug in a setuid root program may allow an otherwise-unprivileged user to wield unauthorized root privileges. Modern distributions minimize the number of setuid-root programs, but attackers still scan systems for them.
