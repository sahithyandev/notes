A program execution is memory safe **iff** none of the following occur:

- Access errors
- Buffer overflow or over-read
- Invalid pointer
- Race condition
- Use after free
- Uninitialized variable or pointer access
- Null pointer access
- Memory leak
- Stack or heap overflow
- Invalid free
- Unwanted aliasing

## Spatial and Temporal Violations

A spatial violation is a memory access outside an object's bounds.

- Buffer overflow
- Out-of-bounds read, e.g. [Heartbleed](/s5/secure-app-dev/heap-overflow#heartbleed)
- Null pointer dereference

A temporal violation is a memory access referring to an invalid object.

- Use after free
- Double free
- Use of uninitialized memory

Overflows, covered in [buffer overflow basics](/s5/secure-app-dev/buffer-overflow-basics), [heap overflow](/s5/secure-app-dev/heap-overflow), and [integer overflow](/s5/secure-app-dev/integer-overflow), are the most common form of spatial violation.

## Memory Safe Languages

A memory safe language, e.g. Rust, Java, enforces memory safety at compile time or run time. Most code is still written in C/C++.

- C/C++ is supported nearly everywhere.
- Low-level code such as operating systems cannot easily be implemented in memory safe languages.
- Memory safe languages are still not fully mature.

Adopting a memory safe language costs runtime overhead and loses some direct, low-level memory access, e.g. hardware-specific instructions needed by device drivers. C and related languages allow direct memory access without bounds checks, hence their vulnerability and large legacy of unsafe code.
