An authentication protocol lets a User and a Server verify each other and set up a shared session key.

## Security objectives

1. The User authenticates that it is talking to the correct Server.
2. The Server authenticates that it is talking to the correct User.
3. A shared secret session key $k$ is established for the session.

The protocol must not be susceptible to:

- man-in-the-middle attacks  
  An attacker sits between User and Server, relaying and possibly altering messages while each side believes it talks directly to the other.
- cut-and-paste attacks  
  An attacker takes valid fields from one protocol message and recombines them into a new message that passes checks in another context.
- replay attacks  
  An attacker records legitimate messages and resends them later to impersonate a party or force reuse of an old session key.

## Common assumptions

- The User with user ID $U_{id}$ shares a secret password $pwd$ with the Server with server ID $S_{id}$. The password stays secret and has enough entropy.
- The User has an authentic copy of the Server's public key in a digital certificate.
- "encrypted under $k$" means symmetric encryption with the session key $k$. Checking a password against the stored record and validating a certificate against the CA are assumed available.
- Session keys and nonces come from a good random source.

## Server has a public encryption key

The Server has an encryption key pair $(PK_S, SK_S)$, with $PK_S$ in its certificate. The User picks the session key $k$.

1. The User sends its ID $U_{id}$ and, under the Server's public key $PK_S$, its password and a fresh session key $k$.  
   Only the Server can decrypt this.
2. The Server decrypts with $SK_S$ and checks the password against the stored record.  
   A match authenticates the User.
3. The Server returns $S_{id}$ and $U_{id}$ encrypted under $k$.  
   Only a party that decrypted the first message knows $k$.
4. The User decrypts and confirms it gets $U_{id}$ back.  
   This proves the peer holds $SK_S$, so it is the real Server.

Only $SK_S$ decrypts the first message, so only the real Server can return $k$; the password in that message authenticates the User. Man-in-the-middle and cut-and-paste fail without $SK_S$. There is no nonce, so freshness rests entirely on the User choosing a new random $k$ each run; reusing $k$ makes the first message replayable.

## Server has a digital signature key

The Server has a signing key pair, with the verification key $PK_S$ in its certificate. The User generates a fresh RSA encryption key pair $((e_U,n_U), d_U)$ and a random nonce $r$. The Server picks the session key $k$.

1. The User sends its ID $U_{id}$, the nonce $r$, and its fresh public encryption key $(e_U, n_U)$.
2. The Server signs $r$ and returns the signature $\sigma$ with $k$ encrypted under the User's public key.  
   The signature binds the reply to the User's nonce.
3. The User verifies $\sigma$ against the $r$ it sent, then decrypts $k$ with $d_U$.  
   A valid signature on the fresh nonce authenticates the Server and rules out replay.
4. The User sends its ID and its password encrypted under $k$.
5. The Server recovers the password and checks it against the stored record.  
   This authenticates the User.

The signed nonce $r$ gives freshness, so replay of the Server's message fails. But the signature covers only $r$, not $U_{id}$ or $(e_U, n_U)$, so a man-in-the-middle can substitute its own public key in the first message, learn $k$ from the reply, and relay the rest. Signing $r\,\|\,U_{id}\,\|\,(e_U,n_U)$ closes this.

## Server has a Diffie-Hellman public key

Public parameters: a generator $g$ of $\mathbb{Z}_p^*$ and a large prime modulus $p$. The Server's long-term DH public value $Y_S = g^{x_S} \bmod p$ is in its certificate. The User generates a fresh DH pair $(Y_U, x_U)$ with $Y_U = g^{x_U} \bmod p$. The session key is the shared value $k = g^{x_U x_S} \bmod p$.

1. The User sends its ID $U_{id}$ and its fresh DH public value $Y_U$.
2. The Server sends its ID $S_{id}$ and its long-term DH public value $Y_S$.
3. The User checks with the CA that $Y_S$ is certified for $S_{id}$, then computes $k = Y_S^{x_U} \bmod p$.
4. The Server computes the same key $k = Y_U^{x_S} \bmod p$.
5. The User sends its ID and its password encrypted under $k$.
6. The Server recovers the password and checks it against the stored record.  
   Only the Server holding $x_S$ for the certified $Y_S$ could have computed $k$, so this authenticates the Server too.

Computing $k$ needs $x_S$ matching the certified $Y_S$, which authenticates the Server; the password sent under $k$ authenticates the User. A man-in-the-middle that swaps $Y_U$ shares a key with the Server but cannot supply $pwd$; one that swaps $Y_S$ fails the CA check. $Y_S$ is static, so there is no server-side freshness and no forward secrecy; a fresh $x_U$ per run keeps $k$ fresh.
