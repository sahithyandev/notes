Aka. Unified Modeling Language. A standard visual language for modeling software systems. Describes both static structure and dynamic behavior.

Used to:

- Design a system before coding.
- Document system architecture.
- Communicate design with stakeholders.
- Analyze business processes.

## Structure Diagrams

Represent the static organization of a system. Capture relationships between components at a point in time.

### Class Diagram

Represents classes, their attributes, methods, and relationships. The primary artifact of object-oriented design.

#### Class Notation

A class is drawn as a rectangle split into three horizontal compartments:

1. Class name, centered. Abstract class names are italicized.
2. Attributes.
3. Operations (methods).

Attribute syntax: `visibility name: type [multiplicity] = defaultValue`

Operation syntax: `visibility name(paramName: type): returnType`

Visibility symbols:

- `+` public
- `-` private
- `#` protected
- `~` package

Static members are underlined. Abstract members are italicized.

An interface is drawn as a class rectangle with `<<interface>>` above the name. Attributes are omitted; only operation signatures appear.

#### Relationships

| Relationship | Line   | Marker                                 | Meaning                                                                                     |
| ------------ | ------ | -------------------------------------- | ------------------------------------------------------------------------------------------- |
| Association  | Solid  | Open arrowhead (optional)              | Navigable link between two classes. Arrow tip shows navigation direction.                   |
| Aggregation  | Solid  | Hollow diamond at the whole end        | "Has-a" where the part can exist independently.                                             |
| Composition  | Solid  | Filled diamond at the whole end        | "Has-a" where the part's lifecycle is tied to the whole.                                    |
| Inheritance  | Solid  | Hollow triangle pointing to superclass | Subclass extends superclass.                                                                |
| Realization  | Dashed | Hollow triangle pointing to interface  | Class implements an interface.                                                              |
| Dependency   | Dashed | Open arrowhead at target               | One class uses another without owning it. Stereotypes: `<<use>>`, `<<call>>`, `<<create>>`. |

#### Multiplicity

Written at each end of an association line:

- `1` exactly one
- `0..1` zero or one
- `*` zero or more
- `1..*` one or more
- `n..m` between $n$ and $m$ inclusive

#### Drawing Steps

1. Identify all classes and interfaces.
2. Add attributes and operations to each compartment.
3. Draw relationships as lines with appropriate arrowheads and diamonds.
4. Annotate each end of every association with multiplicity.
5. Label roles on association ends when the relationship needs clarification.

### Package Diagram

Organizes model elements into named groups and shows dependencies between groups. Used to enforce layering and manage large models.

#### Notation

Package  
 Drawn as a large rectangle with a smaller tab on the upper-left corner. The package name goes in the tab, or centered in the body if the body contains no visible members.

Dependency  
 A dashed arrow from the dependent package to the package it depends on.

#### Stereotypes

`<<import>>`  
 Public import. All public elements of the target become accessible in the source's namespace and are re-exported.

`<<access>>`  
 Private import. Elements become accessible but are not re-exported.

`<<merge>>`  
 The source package's content is merged with the target's. Used for profile extensions.

#### Qualified Names

Elements inside a package are referenced as `PackageName::ElementName`. Nesting uses `Outer::Inner::Element`.

#### Drawing Steps

1. Identify all major subsystems, layers, or modules.
2. Assign classes, interfaces, and other elements to packages.
3. Draw dependency arrows showing which packages depend on which.
4. Add stereotypes to clarify the nature of each dependency.
5. Verify no circular dependencies exist between packages.

### Other Structure Diagrams

Component Diagram  
 Shows system components and their provided/required interfaces.

Deployment Diagram  
 Shows how software artifacts are distributed across hardware nodes.

Object Diagram  
 A snapshot of class instances and their links at one moment in time.

Composite Structure Diagram  
 Shows the internal structure of a class and the collaborations it uses.

## Behavior Diagrams

Describe how a system behaves in response to stimuli or events over time.

Types of stimuli:

- Data stimuli: input data that triggers processing.
- Event stimuli: discrete events that trigger actions.

### Use Case Diagram

Shows system functionality from an actor's perspective. Captures what the system does, not how.

#### Notation

Actor  
 An entity that interacts with the system from outside. Drawn as a stick figure for human users. Drawn as a rectangle labeled `<<actor>>` for external systems.

Use Case  
 A single piece of observable functionality. Drawn as an oval with a short verb-phrase label.

System Boundary  
 A rectangle enclosing all use cases. The system name is written at the top.

Association  
 A solid line between an actor and a use case. Means the actor participates in that use case.

#### Relationships Between Use Cases

`<<include>>`  
 The base use case unconditionally delegates to the included use case. Drawn as a dashed arrow pointing from the base to the included use case. Factor out behavior shared by multiple use cases.

`<<extend>>`  
 The extending use case conditionally inserts behavior into the base. Drawn as a dashed arrow pointing from the extending use case to the base. The base declares an extension point where insertion occurs.

Generalization  
 A use case or actor inherits from another. Drawn as a solid line with a hollow triangle arrowhead pointing to the parent.

<Note>

`<<include>>` means "always runs as part of this." `<<extend>>` means "sometimes adds to this." The arrow direction is opposite: include points to what is called; extend points to the base being extended.

</Note>

#### Drawing Steps

1. Draw the system boundary rectangle and label it.
2. Place all actors outside the boundary.
3. Draw ovals for each use case inside the boundary.
4. Connect each actor to the use cases it initiates or participates in.
5. Add `<<include>>` arrows for shared sub-flows.
6. Add `<<extend>>` arrows for optional or conditional behavior.
7. Add generalizations between actors or use cases that share structure.

### Sequence Diagram

Shows the chronological order of messages exchanged between participants for one specific scenario. Draw one diagram per use case or scenario.

#### Notation

Lifeline  
 A vertical dashed line representing one participant over time. A labeled rectangle sits at the top with the format `objectName: ClassName` (omit the name if the object is anonymous: `: ClassName`).

Activation Bar  
 A thin rectangle overlaid on a lifeline. Marks the period during which the object is actively executing.

Synchronous Message  
 A solid arrow with a filled triangular arrowhead. The sender blocks until the receiver returns.

Return Message  
 A dashed arrow pointing back from receiver to sender. Label with the return value when relevant.

Asynchronous Message  
 A solid arrow with an open arrowhead. The sender does not wait for a return.

Self-Message  
 An arrow that leaves and returns to the same lifeline. Represents a method calling itself or an internal call.

Create Message  
 A dashed arrow labeled `<<create>>`. Points to the rectangle of a new lifeline that begins at that vertical position.

Destroy Message  
 An arrow labeled `<<destroy>>`. The target lifeline ends with a large `X`.

#### Combined Fragments

A combined fragment is a rectangular box with a label called the interaction operator in the top-left pentagon.

`alt`  
 Alternatives. Divided by horizontal dashed lines. Each partition has a guard in square brackets. Only the partition whose guard is true executes.

`opt`  
 Optional. Contains one partition. Executes only if the guard is true.

`loop`  
 Repetition. Labeled `loop(min, max)` or with a guard condition. Repeats while the guard holds.

`par`  
 Parallel. Each partition executes concurrently.

`ref`  
 Reference. Contains the name of another sequence diagram. Represents a call to that diagram.

`break`  
 On a true guard, executes its partition and then exits the enclosing fragment entirely.

Guards are written in square brackets: `[condition]`.

#### Drawing Steps

1. List all participants across the top as lifeline boxes.
2. Draw vertical dashed lifelines downward from each box.
3. Add messages as horizontal arrows, earliest at the top.
4. Add activation bars to mark execution periods.
5. Wrap conditional blocks in `alt` fragments with guards.
6. Wrap loops in `loop` fragments.
7. Label all messages with the method name and key parameters.

### State Diagram

Shows all states an object can occupy and the transitions between them triggered by events. Models the lifecycle of a single class instance.

#### Notation

State  
 A rounded rectangle with the state name centered inside.

Transition  
 A directed arrow from a source state to a target state.

Transition label syntax: `event [guard] / action`

- `event`: the trigger that fires the transition.
- `[guard]`: optional boolean condition that must hold.
- `/action`: optional behavior executed during the transition.

All three parts are optional. A transition with no label fires automatically when the source state's `do` activity completes.

Initial Pseudostate  
 A solid filled circle. Has no name. One outgoing transition leads to the first real state.

Final State  
 A solid filled circle surrounded by a thin ring. Represents the end of the object's lifecycle.

#### Internal Activities

Written inside the state box below the state name, separated by a thin line:

- `entry / action`: runs once when the state is entered.
- `exit / action`: runs once when the state is exited.
- `do / activity`: runs continuously while the object remains in the state. Interruptible by transitions.

#### Composite State

A state containing a nested state machine. Drawn as a rounded rectangle with sub-states inside. Used when a state has complex internal behavior that needs its own states and transitions.

On entry, the composite state's own initial pseudostate is activated unless a transition enters directly to a specific sub-state.

#### History Pseudostate

A small circle labeled `H` inside a composite state. When re-entering the composite state via the history pseudostate, control resumes at the last active sub-state rather than at the initial pseudostate.

Deep history (`H*`) applies this behavior recursively through all nesting levels.

#### Drawing Steps

1. List every distinct condition the object can be in as a named state.
2. Add the initial pseudostate with a transition to the starting state.
3. Add a final state if the object's lifecycle ends.
4. For each state, identify every event that can occur while in it.
5. Draw a labeled transition arrow for each event.
6. Add `entry`, `exit`, and `do` activities to states that need them.
7. Group states that share context into composite states.

### Interaction Diagrams

A category of behavior diagrams that model message exchanges between objects. Each type presents the same underlying interaction in a different format.

Types:

- Sequence diagram (covered above)
- Communication diagram
- Interaction overview diagram
- Timing diagram

#### Communication Diagram

Shows the same information as a sequence diagram but emphasizes object structure rather than time ordering. Also called collaboration diagram.

##### Notation

Object  
 A rectangle labeled `objectName: ClassName`.

Link  
 A solid line between two objects that exchange messages.

Message  
 A labeled arrow along a link. The label format is: `sequenceNumber: methodName(args)`.

Sequence Number  
 An integer prefix that establishes message order: `1`, `2`, `3`. Sub-calls within a message use dotted notation: `1.1`, `1.2`, `1.1.1`.

Condition  
 Written in square brackets after the sequence number: `1 [x > 0]: update()`.

Iteration  
 Written with an asterisk: `1*: process()`. Add a guard for the condition: `1* [i < n]: step()`.

##### Drawing Steps

1. Draw all participating objects as rectangles.
2. Connect objects that communicate with solid lines.
3. Label each message with a sequence number and method signature.
4. Use dotted-number nesting to show calls made within another call.
5. Add guards and iteration markers where needed.

#### Interaction Overview Diagram

Combines activity diagram notation with inline sequence diagram fragments. Shows when and in what order interactions occur across an entire use case.

Structure:

- Uses activity notation: initial node, control flow arrows, decision diamonds, merge nodes, fork bars, join bars.
- Each action node holds either an `inline` sequence diagram or a `ref` tag naming another sequence diagram.
- Decision nodes show guards as `[condition]` on outgoing flows.

#### Timing Diagram

Shows state or condition changes of objects along a horizontal time axis. Used for real-time or time-constrained behavior.

Notation:

- Each object occupies a horizontal swimlane.
- State changes appear as vertical transitions on a waveform-style line.
- Time constraints are written as intervals between transitions.

### Activity Diagram

Shows system workflows, decision points, and parallel processes. Equivalent to an enhanced flowchart.

Notations:

- Initial node: filled circle.
- Activity: rounded rectangle.
- Decision: diamond with one incoming and multiple guarded outgoing flows.
- Merge: diamond with multiple incoming and one outgoing flow.
- Fork: horizontal bar splitting one flow into concurrent flows.
- Join: horizontal bar synchronizing concurrent flows.
- Final node: circle with a filled inner circle, or an `X` inside for flow-final.
- Swimlanes: vertical partitions assigning activities to responsible parties.

### Other Behavior Diagrams

Communication Diagram  
 Focuses on structural links between objects and message sequencing along those links.

Collaboration Diagram  
 UML 1.x name for what UML 2 calls the communication diagram.

## Executable UML

Aka. xUML. A subset of UML that allows automatic transformation of models into executable code.

Core model types:

- Domain models
- Class models
- State models

Supporting technologies:

- Object Constraint Language (OCL)
- UML action language
